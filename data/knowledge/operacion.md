# Runbook de operación Kubernetes simulada
La telemetría actual se consulta con kubectl get alerts -A -o json en el simulador. Se cuentan solo las alertas con status firing. P1 es crítico, P2 importante, P3 limitado. Una alerta resolved no es activa. Para priorizar se atienden las P1 antes de P2 y P3; si varias P1 compiten, se necesita evidencia de impacto para decidir entre ellas.
Los deployments contienen replicas deseadas y readyReplicas disponibles. kubectl -n payments get deployments checkout-api -o json verifica checkout-api. kubectl -n shipping get endpoints dispatch-api -o json verifica readyAddresses de dispatch-api; cero significa ausencia de endpoints listos. kubectl -n web get pods -o json permite ver CrashLoopBackOff y restarts.
Una alerta de HTTP 5xx no demuestra por sí sola una causa raíz. Se deben revisar logs, eventos, métricas de dependencias y cambios recientes antes de afirmarla. No se dispone de consumo de CPU, secretos, costos cloud ni datos financieros en este entorno.
